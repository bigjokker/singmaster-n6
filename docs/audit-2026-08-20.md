## The one correctness gap

**Nothing checks that the coverage claims union to the full range.** The claim
behind `N(m) = 6` is that *every* `k` in `[2, kmax]` except `{K, K+1}` is
impossible. But each artifact only self-reports its own slice:

| i | witness table covers | gap below | covered instead by |
|---|---|---|---|
| 3–7 | `[201, K-1] u [K+2, kmax]` | `[2, 200]` | `fibonacci_i1-7.json`, an exact scan |
| 8 (Q4 run) | `[3, K-1] u [K+2, kmax]` | `k = 2` only | `modular_i8_k400.json` |
| 9 | `[81, K-1] u [K+2, kmax]` | `[2, 80]` | `modular_i9_k80.json` |

`witness.coverage()` verifies completeness *of the range the sweep claimed*,
which is not the same thing. The union is assembled by a human reading three
files, and the evidence types differ (exact inversion vs modular witness vs
sweep witness). This is the same shape as the bugs that produced false `clean`
certificates earlier: a local check passing while the global claim goes
unchecked.

## Speed

Two large, concrete gaps, both measured with identical output confirmed.

### `first_live_after` rescans the interval list from index 0 on every call

At i=9 there are 7,161 live intervals and 28.3M Z-jump columns.

| | per call | over all i=9 columns |
|---|---:|---:|
| linear scan from index 0 | 292.5 µs | **2.30 h** |
| `bisect` to the right interval first | 2.1 µs | **0.02 h** |

**142×**, same answers. This is single-threaded work in the parent, before any
worker starts — it is exactly the stretch during which the running i=9 job
looked idle earlier today.

### `binom_mod_lucas` does not use the δ-identity

For a two-digit prime the generic Lucas costs `min(k0, n0-k0)`; the δ-identity
costs `delta-1` where `delta = (alpha+1)p - N`, and δ is small at a cell bottom.

| p (i=9) | `min(k0, n0-k0)` | `delta-1` | Lucas | δ | |
|---:|---:|---:|---:|---:|---:|
| 37,024,903 | 8,740,323 | 115 | 737.6 ms | 0.021 ms | **34,629×** |
| 24,683,233 | 3,601,231 | 8 | 300.1 ms | 0.009 ms | **33,347×** |

Same answer both ways. `r_two_digit_delta` already exists and the sweeps use
it; `binom_mod_lucas` does not, and it is the r(p) route for the `modular`
command, `nextprime_sweep`, and — most importantly — `witness.lucas_mod_pure`,
where it is a large share of the cost of verifying one certificate.

### Size-law accuracy is a large-p claim

The 0.2% quoted in the docs is measured at `p ~ 10^6`. Against exact image
sizes at smaller `p` the error is larger:

| p | worst error in the sweep regime (`g/p <= 0.25`) |
|---:|---:|
| 1009 | 5.6% |
| 10007 | 1.9% |

Irrelevant for Band II and the Z-jump, which run at `p >= 10^5`. It is not
obviously irrelevant for the small-`k` census, which uses primes in the
hundreds, and where an error compounds over a run.

## Questions

### Q19. Should `first_live_after` bisect into the interval list? *(low · **HARD**)*
Measured 142× (292.5 → 2.1 µs/call) with identical answers, turning 2.3 h of
serial parent time at i=9 into 1.2 minutes. Decidable by implementing the
bisect, asserting identical output over a large contiguous `k` range, and
re-measuring. The only subtlety is that `live_intervals` sorts by `lo` and may
overlap, so the bisect must land on or before the containing interval and then
walk forward — which is what the measured variant does.

### Q20. Should `binom_mod_lucas` take the δ-identity branch? *(low · **HARD**)*
Measured 33,000–35,000× at i=9 two-digit primes with the same answer.
Decidable: add the branch guarded by `p*p > N`, assert agreement against the
generic route over several hundred primes per member, and measure the effect on
`modular`, `nextprime_sweep`, and certificate verification.

**One sub-question that is genuinely EXTRA**, and should be answered before
touching `witness.py`: the verifier deliberately uses generic Lucas as its
*independent* route, with δ as a cross-check. Making δ primary would remove
that independence. Can δ be primary with full Lucas retained as a sampled
cross-check, without weakening what a certificate asserts? The honest answer
may be "no — keep the verifier slow on purpose".

### Q21. Build a machine-checked coverage ledger. *(low-medium · **HARD**)*
A script that reads every artifact, extracts each claimed range together with
its evidence type (exact inversion, modular witness, sweep witness), and
asserts the union equals `[2, kmax] \ {K, K+1}` for each member — failing
loudly on a gap or an overlap with inconsistent evidence. Decidable, and it
converts the central claim from "three files that together look complete" into
one checkable statement.

### Q22. Should the Z-jump start at `k = 2`? *(trivial · **HARD**)*
i=8's re-derivation starts at `k = 3`, leaving `k = 2` covered only by a
separate artifact. `k = 2` is decided by the `4c+1`-QR test in O(1), so
including it should cost nothing. Decidable: set `K_EXACT` so the Z-jump starts
at 2, confirm the witness table gains exactly one row and still verifies, and
confirm the runtime is unchanged.

### Q23. Is the size law accurate enough at small primes? *(medium · **EXTRA**)*
Measured ~5.6% at `p ~ 10^3` against 0.2% at `p ~ 10^6`; over a run of 8 that
compounds to roughly 50% in Λ. Decidable: for every column in the small-`k`
census, does a ±2× perturbation of Λ change the escalate/ordinary verdict? If
not, document the accuracy bound by regime and stop quoting 0.2% globally. If
so, the trigger needs a wider margin at small `p`. The likely answer is "no
verdict changes" — expected counts there are ~65 against a 0.01 threshold — in
which case the deliverable is the documented bound, not a code change.

### Q24. Re-derive the phase budget now that the table is gone. *(low · **HARD**)*
`profile_sweep.py` times `fact_table`, which Q2 removed from the hot path, so
its "90.6% table" split for i=9 now describes the *old* pipeline and the 29.6 h
Z-jump estimate is stale. Decidable: point the profiler at the windowed path
and re-derive the i=9 and i=10 budgets — which also feeds back into Q11, whose
"i=10 is 65.7 days" figure rests on the pre-Q2 numbers.

## No MAX

Nothing in this audit warrants MAX. MAX is reserved for a question whose
positive answer changes what the project *is*, and every gap found here is
bounded engineering or a documentation-accuracy issue. Q21 is the most
structurally important — it is the only one touching the central claim — and it
is still a scripting job, not a research question. Manufacturing a MAX from
this list would misrepresent it.
